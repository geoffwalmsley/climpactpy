Climpact: redesign proposals

Your feedback was that the help icons look odd and aren't clearly clickable, the app feels cramped, cluttered and same-coloured, controls take a lot of scrolling to reach, and entering data is mixed up with viewing results. Here are seven proposals, in priority order, each with a mockup. The colours and sizes are provisional: once you pick a direction I'll set them as tokens in DESIGN.md and check their contrast.

  1. P1Separate what you enter from what you get: one Inputs panel, read-only results
  2. P1Colour means something: ink for actions, colour only for data and status
  3. P1Help you can see: a labelled Help button at the end of each section header
  4. P2One setup screen, then the workspace: a first visit takes two steps, not four tabs
  5. P2Less box, more space: one surface level, a sticky header, fewer borders
  6. P2Quality as list and detail: the decision stays in view
  7. P3Phones: Inputs collapse into a one-line bar
P1

1. Separate what you enter from what you get

This is the root cause of the clutter. Today every tab mixes the two. Data is a form plus a data report. Quality is a report plus an upload button plus threshold settings hidden in Details. Results is a report plus the "Adjust and recalculate" form, which sits about 3,000px down, below 80 indices. "Edit the details" is a small link under the title. The user can't build a picture of where their settings live.

What changes

  • A left Inputs panel lists everything the user has given: the file, the station, the base period, the quality thresholds and the index settings. Each has an Edit link.
  • Edit opens a side sheet with only that form. It says what applying will update, then Apply (one button).
  • The tabs become read-only outputs: Quality · Results · Files. The Data tab goes: its summary moves into Quality as "Your data".
  • An input changed since the last run is highlighted in the panel, and the run's progress shows beneath it. This uses #179's out-of-date model.

Why

  • One place to change things, so there's nothing to remember (recognition over recall).
  • Settings are one click away from any tab, with no scrolling (Fitts's law).
  • Output pages lose every form, so each becomes shorter and calmer (minimalist design).
  • It matches desktop analysis tools, where parameters sit on the left and results on the right (Jakob's law).

      P1

      2. Colour means something

      Today blue does every job: the primary button, links, the active tab, help icons, chart lines, sparklines, badges and info alerts. When everything is highlighted, nothing is, so the eye has nowhere to land. The fix is to give each colour one job.

      Rules

      • Ink (near-black; near-white in dark mode) for primary buttons, the current tab and links. Links are underlined text, not blue.
      • Brand blue only for the logo, focus rings and selection.
      • Theme colours mark data: Heat, Cold, Rain and Drought each have one hue, used in tile edges, sparklines, chips and index charts. The user learns them once and can then scan by colour.
      • Status colours (green, amber, red) only for the verdict and run state.
      • Every colour still comes with a word or shape, as now.

      3. Help you can see

      The ⓘ is a 14px outline glyph. It's placed after the heading text, so it moves with the heading's length and sits off the baseline. It's the same blue as everything else, and nothing about it says "press me". Fix it with one section-header pattern: title, an optional muted note, then a labelled Help button pinned to the end of the row.

      P2

      5. Less box, more space

      Nearly everything sits in a bordered card, and cards hold tables and charts with their own borders. On Load that's three nested boxes. Borders compete with content, and the 1rem padding between them makes the page feel cramped even though it is long.

      Rules

      • One surface level. Sections are separated by space (48px) and a heading, not boxes. A box only marks something that is one object: a theme tile or a finding.
      • A tinted band, not a card, for the page's one answer: the verdict on Quality, the summary on Results.
      • Tables without frames: hairline rows only.
      • A sticky workspace header (station name, tabs, page actions) so the user always knows where they are and never scrolls back up for a button.

      Type

      • A human station name as the title (from the form, not the file name). The file name moves to the subtitle.
      • Small uppercase labels for groups ("YOUR INPUTS"). They group without adding boxes.
      • Larger, bolder numbers where there's an answer (22 of 80); smaller muted text for the rest.
      • Index codes hidden in tiles and shown in the table, so tiles read as plain language.

      Both mockups above apply these rules: compare the P1 Results tab with the current page's stacked bordered cards and accordions.

      P2

      6. Quality as list and detail

      Quality now stacks the verdict, five finding rows each with their own expander, four groups with their own expanders, a missing-data table and a Details accordion holding the real charts. Reviewing a finding means opening rows one after another, and "Use this data" scrolls out of view. Use a list on the left and the selected item in detail on the right, with the verdict and its buttons pinned at the top.

        Suggested order of work

        1. P2 + P3 + P5 together (colour, help button and spacing tokens, the section-header pattern). This is mostly CSS and components; every page benefits; no flow change. About one PR.
        2. P1 Inputs panel and sheet. This is the structural change: it removes the Data tab and the forms from output pages, and reuses #179's out-of-date model. About two PRs: rail + sheet, then moving each form.
        3. P4 setup screen, which builds on P1.
        4. P6 Quality list-detail.
        5. P7 phone pass, checked throughout but finished last.

        Decisions for you: (a) Is the Inputs panel the right model, or do you prefer a single "Setup" tab? (b) Ink-black primary buttons, or keep a brand-blue primary? (c) Should the station title come from the station name field rather than the file name?
